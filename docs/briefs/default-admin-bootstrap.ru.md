# Business brief: Дефолтный ADMIN при инициализации БД

**Дата создания:** 1 октября 2026, 21:20 (UTC+3)  
**Дата изменения:** 1 октября 2026, 21:30 (UTC+3)

Шаблон **алгоритма A** (новая разработка). Заполняется до спеки. Без API, пакетов и SQL.

См. [`docs/dev-workflow.ru.md`](../dev-workflow.ru.md).

## 1. Проблема

- После чистого развёртывания (новая БД / Docker) в системе нет ни одного ADMIN.
- Первый вход возможен только через ручную правку БД или обходные скрипты — неудобно и рискованно для локальной разработки и первого деплоя.
- Учётные данные «первого» админа должны задаваться окружением (`.env`), а не хардкодом в коде.

## 2. Кто пользователь

- **Оператор / разработчик / DevOps** — настраивает `.env` и поднимает стек.
- После создания учётки входит как **ADMIN** (продуктовая роль).

## 3. Ценность

- «Нулевой» старт без ручных SQL: сразу есть рабочий ADMIN для `/admin/*`.
- Единый источник правды для логина/пароля первичного админа — `.env` / секреты окружения.
- Повторяемые окружения (dev, demo, CI) без сюрпризов «нет ни одного admin».

## 4. Сценарий успеха

1. В `.env` заданы email и пароль первичного ADMIN (имена переменных — в спеке; черновик: `ADMIN_EMAIL`, `ADMIN_PASSWORD`).
2. При старте backend, если в БД **нет ни одного** пользователя с ролью ADMIN в available roles, создаётся учётка:
   - роль/набор: `ADMIN` (active = `ADMIN`);
   - `emailVerified = true`, `active = true`;
   - пароль — хеш из `ADMIN_PASSWORD`.
3. Оператор входит этим email/паролем в UI.
4. Если ADMIN уже есть — повторный старт **не** создаёт второго и **не** перезаписывает пароль существующего.
5. Если переменные не заданы (пусто) — старт **не падает**; в лог пишется предупреждение, что bootstrap-admin пропущен (допущение; см. §6).

## 5. Out of scope (бизнес)

- Смена пароля / email bootstrap-admin при каждом рестарте.
- Несколько seed-пользователей (manager, driver) из `.env`.
- Invite / UI «создать первого admin».
- Замена `SUPER_ADMIN_PASSWORD` (step-up) — это отдельный секрет, не логин-учётка.
- Flutter.

## 6. Ограничения

- Стек: Angular + Java (Flutter не входит).
- Identity = supporting: bootstrap на старте приложения (ApplicationRunner / аналог), не «магия» только в SQL без хеша пароля.
- Пароль в `.env` только для первичного bootstrap; в БД хранится хеш.
- `.env.example` и RUN документируют переменные; секреты не коммитить.
- **Допущения (подтвердить):**
  1. Создавать только если нет ни одного ADMIN (available).
  2. Пустые `ADMIN_EMAIL` / `ADMIN_PASSWORD` → skip + warning, не abort старта.
  3. `emailVerified=true`, `active=true`.
  4. Не трогать пароль/роль, если ADMIN с таким email уже есть (или любой ADMIN уже есть — не создавать).
