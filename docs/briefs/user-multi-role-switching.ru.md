# Business brief: Несколько ролей у пользователя и переключение

**Дата создания:** 1 октября 2026, 11:55 (UTC+3)  
**Дата изменения:** 1 октября 2026, 11:53 (UTC+3)

Шаблон **алгоритма A** (новая разработка). Заполняется до спеки. Без API, пакетов и SQL.

См. [`docs/dev-workflow.ru.md`](../dev-workflow.ru.md).

## 1. Проблема

- Сейчас у учётной записи **одна** роль (`USER` | `MANAGER` | `DRIVER` | `ADMIN`).
- Человек, которому нужны разные контуры (например, менеджер и водитель, или admin и user), вынужден заводить несколько аккаунтов или постоянно просить сменить роль.
- В каноне B02 multi-role явно вынесен в Out of Scope — возможности нет.

## 2. Кто пользователь

- **ADMIN** — назначает пользователю набор доступных ролей.
- **Любой пользователь с ≥ 2 назначенными ролями** — переключается между ними в рамках одной сессии/учётки.
- Затронутые роли продукта: `admin`, `manager`, `driver`, `user` (существующий enum, без новых ролей в этой итерации).

## 3. Ценность

- Один логин — несколько рабочих контекстов без смены пароля и без «лишних» учёток.
- Админ контролирует, какие роли доступны конкретному человеку.
- Меньше путаницы с дублями профилей и доступов.

## 4. Сценарий успеха

1. Новый пользователь при регистрации получает **по умолчанию** роль `USER` (единственная доступная, пока ADMIN не расширит набор).
2. ADMIN открывает карточку пользователя и назначает ему несколько ролей из существующего набора (например, `MANAGER` + `DRIVER`); роль `USER` может остаться в наборе или быть снята по решению ADMIN.
3. Пользователь входит в систему; видит текущую активную роль и список доступных ему ролей.
4. Пользователь переключает активную роль; UI и доступ к функциям соответствуют выбранной роли.
5. Роли, которые ADMIN не назначил, недоступны для переключения и не дают прав на backend.
6. Если у пользователя одна роль — поведение как сейчас: переключатель не нужен / не мешает.

## 5. Out of scope (бизнес)

- Матрица permission / fine-grained права (не роли, а отдельные разрешения).
- Новые роли сверх текущего enum.
- Одновременная работа «под двумя ролями сразу» (активна ровно одна).
- Invite / создание пользователя админом, смена email/пароля админом.
- Impersonation («войти как другой пользователь»).
- Flutter-клиент (заморозка).

## 6. Ограничения

- Стек: Angular + Java (Flutter не входит).
- Identity / Access — supporting-домен: transaction script ок; не раздувать до «полного DDD».
- Существующие проверки RBAC на backend остаются источником правды; UI только отражает активную роль.
- Обратная совместимость: учётки с одной ролью продолжают работать без обязательных действий пользователя.
- Регистрация: новый пользователь по умолчанию получает роль `USER` (как сейчас); дополнительные роли — только через ADMIN.
- Связанные канон-спеки (B01 auth, B02 admin users, частично B03 profile) после принятия фичи нужно будет синхронизировать (дельта в существующих файлах на этапе спеки/сдачи — без параллельного «второго auth»).

## 7. Связь с реестром

- Тема **есть** в каноне как **single-role**: B01 [`auth-authentication-authorization.ru.en.md`](../specs/auth-authentication-authorization.ru.en.md), B02 [`admin-user-management.ru.en.md`](../specs/admin-user-management.ru.en.md) (там multi-role = Out of Scope).
- Это **новая возможность** вне freeze-границы «одна роль» → старт по **алгоритму A** (новая спека), с последующим обновлением связанных B01/B02 (убрать multi-role из Out of Scope, описать контракт).
- Не алгоритм B «в чистом виде»: меняется модель доступа, а не точечная правка уже описанного поведения.
